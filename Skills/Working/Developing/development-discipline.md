# 开发纪律（对齐 · TDD · 调试）

> 改编自"带文档盘问 / tdd / 诊断 bug"的实战方法，本地化到本仓库的工作流（工单/邮件输入 → work-triage → 用户故事 → IaC）。核心思想：**反馈速度就是你的速度上限**。先对齐，小步走，靠证据行动。

---

## 这个技能在工作流中的位置

```
邮件/工单 → work-triage → devops-userstory-creation
    → 阶段 1（对齐需求）
    → 阶段 2（TDD 实现）
    → commit → 如果出问题 → 阶段 3（有纪律的调试）
```

三个阶段相互独立——你不一定每次都跑全部。**经验法则：变更越接近生产、或请求越含糊，就越要往链条前方走。**

---

## 阶段 1 —— 编码前对齐（轻量盘问）

**何时：** 需求含糊、一行工单、跨团队变更、任何触碰生产资源的事情。产出 = 一条可执行的验收标准（DoD），不是代码。

**步骤：**
1. 列出已知信息：环境、范围、负责人、错误/预期输出（从工单/邮件中提取，按 email-preparation 的做法）。
2. 盘问每个"不清楚"的点：做了会怎样 / 不做会怎样 / 谁在用 / 失败的影响半径是什么。**一次只问一个问题**，等回答。
3. 如果项目有共享行话（例如平台特有术语），用那些术语重述需求并确认没有歧义。
4. 产出 2–4 行的验收标准：`Given <环境> / When <动作> / Then <预期结果>`。
5. 进入阶段 2 前与用户确认。**确认前不写代码。**

**产出：** 验收标准放到相关 Artifacts 目录（`Working/Artifacts/<skill-id>/`）或直接写进用户故事描述。

**踩坑：**
- "大概就这意思" ≠ 确认。没有可验证的 *Then*，就没有对齐。
- 不要一次连问 10 个问题；最多 3 个，一次一个。

---

## 阶段 2 —— 小步 TDD

**何时：** 任何真实的代码/IaC 变更（Terraform 模块、Bicep、脚本）。不是"每个 hello-world 都要测试"——而是**一次一个垂直切片，每个切片都有验证**。

**步骤（红绿重构）：**
1. **红：** 先写一个会失败的验证。Terraform 用 `terraform validate` + 关键资源的 `plan` 断言；脚本用测试框架。
2. **绿：** 写能通过的最小实现。不要一次搭整个模块——每个切片一个关注点。
3. **重构：** 保持绿色状态下清理。命名、抽取公共逻辑。
4. 重复直到用户故事的所有切片完成。
5. 提交前，运行完整的 `plan`（或 CI）并把 diff 给用户看。

**为什么这在本仓库很重要：** 编排平台是带远程 state 的执行面，所以 **plan 就是你的测试**——plan 断言比单独的单元测试更能防止生产事故。

**产出：** 每个切片 = 验证证据（plan 输出 / 测试结果），记录在 commit message 中。

**踩坑：**
- 不要跳过红直接写实现——从来没失败过的验证，让"绿"毫无意义。
- plan diff 中出现意外的资源变更 = 立即停下，回到阶段 1，或检查 state 漂移（见 infrastructure-as-code 的踩坑）。
- 绕过模块契约的模板侧"快速修复"是长期债务；用正确的方式测试。

---

## 阶段 3 —— 有纪律的调试

**何时：** 变更后出错、部署被阻塞、资源状态诡异。**这补充了排障技能**——那些告诉你*查什么*，这个告诉你*怎么查*。

**步骤（复现 → 最小化 → 假设 → 取证 → 修复 → 回归）：**
1. **复现并变红：** 拿到完整原始错误（时间戳、资源名、操作者）；先复现，不要猜。
2. **最小化：** 砍掉不相关的变量——锁的问题还是代码的问题？state 的问题还是模板的问题？隔离到最小范围。
3. **假设：** 写一行假设（"因为 X，所以 Y"）；只测这一个。
4. **取证：** 加日志 / plan / state 查询来拿证据——**用证据确认或反驳，而不是直觉**。
5. **修复：** 最小变更；不要顺手重构。
6. **回归：** 确认原始错误消失 + 相邻功能没坏。**留下一条排障记录**（写入相关排障技能或 Artifacts）。

**产出：** 根因（一句话）+ 修复变更 + 回归证据。

**踩坑：**
- 跳步是最大的错误。直接改代码 = 把生产当试验台。
- 每个假设的"证据"必须可复现——同样的 plan 输出或同样的日志。
- merge/rebase 冲突：按意图逐块解决；**不要 `--abort` 重来**。

---

## 模型调用约定

- **用户主动调用：** 本技能由用户显式触发（输入触发短语）。
- **模型主动调用：** 当调整任务时（用户说"帮我改这个"但需求不完整，或变更后报错），模型**自动**调用对应阶段，无需被要求。
- 决策规则：需求含糊 → 阶段 1；触碰代码/IaC → 阶段 2；错误调试 → 阶段 3。

---

## 何时不使用本技能

- 纯查询/解释（"这个错误是什么意思"）→ 用排障技能。
- 规格清晰 + 用户只要执行 → 跳过阶段 1，直接进阶段 2。
- 一次性临时脚本、用户明确说"不需要验证" → 跳过阶段 2，但至少跑一次 plan。
