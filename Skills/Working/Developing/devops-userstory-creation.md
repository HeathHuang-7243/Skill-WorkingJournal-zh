# DevOps 用户故事编写（IaC 前置条件）

> 这是**代码 / IaC 变更的规划门禁**。根据 [`work-triage.md`](./work-triage.md) ④：任何代码变更（包括基础设施即代码）都必须先开 DevOps 用户故事，并与**自动化负责人**和**平台首席架构师**对齐。
> 本技能是 [`infrastructure-as-code`](./infrastructure-as-code.md) 的**前置条件**——没有用户故事，就没有 IaC。

## 为什么用户故事必须先于代码（而不是代码先行）
- 代码变更（IaC 模板、编排流水线、应用代码）直接影响平台治理和成本；先有 Story 可以在工作开始前对齐范围、暴露策略/成本影响。
- 它是**规划产物**，不是**审批产物**：真正的部署审批是另一条线（变更请求，见 work-triage ④）。不要把两者混在一起。

## 何时需要
- [ ] 任何**代码变更**（应用代码、IaC 模板 / Bicep / Terraform、编排配置）
- [ ] 创建 / 修改**策略**，或**产生成本**的变更（两者都必须在 Story 中显式标注）
- [ ] 任何会进入主分支 / 被部署的内容

## 如何创建（模板字段）

### 录入
- [ ] **Area Path** = `<看板>`、**Iteration** = `<看板>\<年份>\<季度>`（你的标准录入位置）
- [ ] **标题** —— 简短具体（例如"新平台数据库备份"），不要用"改进 X"这种含糊的
- [ ] **标签** —— 按故事主题的跨领域分类标签

### 故事正文（严格的"作为…我希望…以便…"）
- [ ] **作为** [角色] —— 你行动所在的角色/视角。常见：
  - `<角色 A>` —— IaC / 合规 / 备份类故事
  - `<角色 B>` —— 编排工作流 / 结构类故事
- [ ] **我希望** [动作] —— 动词开头，**必须落到具体的工具或对象上**：
  - ✅ "**通过 Terraform 脚本**部署所有运行 SQL Database 服务的 Windows Server（基于 IaaS）"
  - ❌ "改进备份"（没说用什么、针对什么）
- [ ] **以便** [结果] —— 治理 / 平台目标（不是"业务功能完成了"）：
  - ✅ "所有 SQL Database 都有备份保护，降低数据丢失风险"
  - ✅ "通过平台部署的资源符合策略合规"

### 详情
- [ ] **描述** —— 当前问题 + 原因。复杂背景可以外链到 wiki 页面；Story 里保留链接 + 一行摘要。
- [ ] **验收标准** —— 每条都是**可验证的要点**（测试/审计能通过/不通过)；避免"良好"这类含糊词。粒度随任务类型变化：
  - IaC 交付 → 细（约 7 条：提供模块、默认启用、配置已调和、大小暴露为变量…）
  - 治理追踪 → 粗（约 3 条：识别违规、发起工作坊、决定缓解/豁免）
  - 重构 → 中等（约 4 条：结构对齐、组已移动、KB 已创建、交接）
  - **修正型**（修复过期的策略/配置值）→ 在 IaC 交付粒度基础上，**强制额外 2 条**：(a) 在 PR 描述中记录被替换的**旧值**，以便审计追溯；(b) 验证**现有引用不被破坏**——无未版本化的资源重命名、无破坏性参数变更（除非在 PR 中显式声明并获批）。
- [ ] **完成的定义** —— 收敛到 1–2 句话，例如"文档已更新并获批；验收标准已满足。"

### 规划
- [ ] **优先级** —— 与你的标准值保持一致
- [ ] **开始日期 / 目标日期** 必填；**截止日期** 可选

### 参考 / 风险 / 分类（标准值）
| 字段 | 标准值 | 备注 |
|-------|----------------|-------|
| 变更请求编号 | `<NCR>` 或留空 | NCR = 本次变更自带单独的变更请求；留空 = 由另一个 CR 追踪 |
| 变更类别 | `Infrastructure`（示例） | 按你的组织 |
| 变更范围 | `None` | 除非有跨领域影响 |
| 子类型 | `None` | 除非需要更细粒度 |
| 风险等级 | `Low`（默认）/ `Medium` | **新机制 / 新策略 / 跨团队协作 → Medium**。**修正现有策略以对齐现有标准**（且不降低保护）保持 **Low**——要区分"新"与"修正"，不要把每个策略变更都一律标成 Medium。 |
| 风险缓解 | `Not necessary` / `Action needed` | 与风险等级同步 |
| 价值领域 | `Deployment`（示例） | 按你的组织 |
| 阻塞 | `No` | 阻塞通过状态/链接表达，不用这个字段 |
| 平台 | `<平台>` | 你平台的固定值 |

### 协调 / 链接
- [ ] **自动化负责人 + 平台首席架构师** —— 对齐范围与实现方式
- [ ] Story 触及策略创建/变更 → **策略负责人** 在 Story 阶段评审
- [ ] **相关工作** 链接父/子故事
- [ ] **开发区块** 链接 GitHub commit / PR / 分支；PR 引用该 Story 以便追溯
- [ ] 实现开始前将故事状态设为 `Ready` / `Active`

## 模式（从真实故事中提炼）
- 字段齐全：Priority / Category / Value area / Platform 全部设置——不靠空白猜测。
- 严格的"作为…我希望…以便…"，无变体。
- **角色随主题切换**：IaC/合规 → `<角色 A>`；编排工作流 → `<角色 B>`。选择角色 = 你当前正在调用的能力——这是**视角切换**，不是头衔。
- **动作必须落到工具/对象上**：不是"要做什么"，而是"用**什么**、针对**什么**"。
- **结果总是指向治理/平台目标**：备份基线 / 策略合规 / 与租户结构对齐——不是"业务功能完成"。
- **AC 粒度跟随任务类型**（见上表）。
- **描述可以外链**：复杂上下文放 wiki；Story 保留链接 + 一行摘要。

## 与变更请求的顺序（重要——不要混）
1. **DevOps 用户故事**（本技能）——规划门禁，在代码/IaC 变更之前。与自动化 + 平台对齐。
2. **实现**（写 IaC / 代码，开 PR）。
3. **变更请求**——部署之前；你自己准备，然后获批（见 work-triage ④）。

> 用户故事 ≠ 变更请求。前者管*做什么/为什么*；后者管*能否上线*。

## 踩坑 / 教训
- 没有用户故事就改 IaC = 跳过治理门禁；work-triage ④ 把这种行为标为升级项——不要跳。
- 自动化负责人和平台架构师都需要有席位——不是二选一。
- 在 Story 阶段标注策略 / 成本影响，而不要在部署突然需要评审时才标。
