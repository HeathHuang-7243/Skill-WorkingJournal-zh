# 解决方案架构设计

> 示例 —— 把个人细节（years、proficiency、项目名）换成你自己的。
> 正文结构自由；本技能使用"叙述 + 决策标准"版式。

## 目的
把业务问题变成一个站得住脚、成本可感知的云架构，团队能构建、运维并演进。产出是一份设计文档 + 一份经过评审的架构图，而不只是一张图。

## 我的方法（叙述）
1. **框定问题。** 捕获功能 + 非功能需求、约束，以及真正的成功指标（延迟？成本？合规？上市时间？）。大多数糟糕架构跳过了这一步，去优化了错误的轴。
2. **把需求映射到支柱。** 对照相关的 Well-Architected Framework（可靠性、安全、成本、性能、运维、可持续性）逐一核对。指出哪个支柱是硬约束——它主导权衡取舍。
3. **画出 2 个以上方案。** 绝不只展示一个。给出一个便宜/简单的方案和一个可扩展的方案，并把取舍说清楚。决策的质量来自对比，不是来自单一的"最优"。
4. **用评审验证。** 在写代码之前，与安全 + 成本 + 运维一起过一遍设计。在这里抓住错误假设，代价是几小时，而不是几周。
5. **记录决策。** 记录所选路径以及被否决的选项 + 原因。当需求变化时，未来的你需要"被否决选项"的上下文。

## 决策标准（我如何选择）
| 关注点 | 优先 | 何时避免 |
|---------|--------|------------|
| 计算 | 托管 PaaS/serverless 应对变动负载 | PaaS 适用时仍用 VM |
| 数据 | 匹配访问模式的托管数据库 | 一个数据库搞定一切 |
| 集成 | 托管事件/队列 | 自定义轮询循环 |
| 成本 | 低基线场景按用量付费 | 常驻的重型基础设施 |

## 任务
- [ ] 需求 + NFRs 已捕获并签字确认
- [ ] 支柱评估完成；明确命名硬约束
- [ ] 画出 ≥2 个带取舍的方案
- [ ] 设计已由安全 + 成本 + 运维评审
- [ ] 记录决策 + 被否决的替代方案

## 踩坑
- "最便宜"和"最简单"是两个不同的轴——两个都要说清。
- 一张没有"被否决替代方案"的架构图是一个未决的设计，不是决策。
