# 云资源锁排障

> 当部署被资源锁阻塞且问题尚未证明与平台编排相关时使用本技能。第一原则：动任何东西之前，先确认锁的确切范围和创建者。

## 本技能接受的输入类型
- 应用/项目团队的邮件线程
- 带截图或粘贴错误的聊天线程
- 来自 IT 请求/事件系统的工单文本
- 部署重跑失败后的自助调查

## 快速分类
- **问题类别：** 部署解除阻塞 / 治理锁
- **典型错误形态：** `ScopeLocked`、`The scope is locked`、`cannot delete lock`、`lock level prevents operation`、重跑老是失败
- **常见范围：** Storage、Key Vault、网络、备份或共享平台资源上的订阅、资源组或资源级锁

## 证据优先工作流

## 已知高信号模式：备份保护锁

如果锁名是 `AzureBackupProtectionLock`（或你平台的等价物），先把它当作备份治理锁，而不是通用平台锁。

典型形态：
- Storage Account 或 Azure File Share 注册到 Recovery Services Vault
- 备份策略已挂接
- Terraform 或门户尝试删除或替换受保护的文件共享
- 平台返回 `409 ScopeLocked`，因为存储账号范围受备份保护

这通常意味着：
- 请求者或其自动化之前启用了文件备份
- 即使部署现在在另一个工具中失败，锁也可能是备份服务系统管理的
- 立即可见的阻塞通常是删除或替换操作，而不是创建本身
- 如果用户想重命名文件共享，Terraform / 编排通常会把它建模为"销毁旧共享 + 创建新共享"，而不是原地重命名

### 备份特定决策路径
1. 确认目标文件共享或存储账号是否在 Recovery Services Vault 中受保护
2. 检查计划中的变更是否包含删除 / 替换行为
3. 如果是，协调受控序列：
  - 如果获批，先从备份中停止保护或移除备份策略 / 受保护项
  - 只有移除备份保护后、且只有必要且获批时，才移除备份保护锁
  - 完成部署
  - 为最终文件共享名和策略重新注册备份
4. 如果不需要删除，检查部署是否可以改为避免破坏性替换

不要在 Prod 或共享存储上盲目移除 `AzureBackupProtectionLock`。它保护备份完整性，通常有请求团队之外的运营所有者。

### 1. 规范化请求
触碰环境前先捕获这些字段：
- 订阅
- 环境（Test / Prod / Shared）
- 资源组和资源名
- 精确错误文本和时间戳
- 请求的动作：创建 / 更新 / 删除 / 部署重跑
- 请求者是否确认自己没有锁删除权限

### 2. 证明锁存在及其位置
检查三个可能范围：订阅、资源组、资源。
捕获：
- 锁名、锁类型（`CanNotDelete` 或 `ReadOnly`）、备注/描述、范围路径
- 是否存在多个继承的锁

### 3. 确定所有者和来源
按这个顺序使用证据：
1. Activity Log 中的锁 `write`/`delete` 事件
2. 锁备注、标签或命名约定
3. 创建时间戳附近的流水线 / 自动化运行
4. 资源变更历史或平台变更记录

决策：
- 证据指向你的编排平台 → 切换到 `deployment-lock-troubleshooting`
- 证据指向其他自动化或平台所有者 → 路由给该所有者
- 证据不明确 → 带证据包升级，而不是猜测

### 4. 决定是否允许解锁
- **Test / 非生产：** 通常风险较低，但仍只移除最小必要范围
- **Prod / 共享范围：** 解锁前需要明确的所有者审批
- **ReadOnly 锁：** 预期创建/更新和删除都会失败
- **CanNotDelete 锁：** 删除操作失败，但如果部署不是替换受保护资源，创建/更新可能仍然有效
- **备份保护锁：** 先假定备份归属；改锁前检查保管库保护状态

### 5. 安全解除阻塞
- 优先解锁资源而不是 RG，优先 RG 而不是订阅
- 只移除或调整直接阻塞部署的那把锁
- 记录谁批准的变更以及时间
- 重跑一次部署
- 如果保护本应保留，重新应用锁

### 6. 收尾
回复包含：
- 根因：哪把锁阻塞了动作
- 来源：谁或什么创建了它
- 范围：资源 / RG / 订阅
- 采取的动作：移除、降级或路由
- 结果：部署通过/失败
- 后续：重新应用保护、改进自动化或记录所有者

## 最小证据包
- 锁详情的截图或导出
- 锁创建或删除的 Activity Log 记录
- 失败部署的时间戳及与目标资源的关联
- Prod 或共享范围解锁的审批备注
- 涉及备份保护锁时：保管库名、备份策略名、受保护项详情

## 如何读 Terraform 失败
- 如果 Terraform 显示对现有共享 `destroy` 和新建 `create`，这次运行是在执行替换，不是纯新增。
- 如果错误说共享无法删除因为存储账号范围被锁，真正的阻塞是高层的存储账号锁，不是共享对象本身。
- 在文件备份场景中，这通常发生在共享名改变、`for_each` key 改变，或受保护共享被替换时。

## 这个确切模式的推荐动作
- 确认锁是存储账号上的备份保护锁。
- 确认旧文件共享当前被保管库和策略保护。
- 决定旧共享是必须真的删除，还是 IaC 可以避免替换。
- 如果用户实际上是在重命名共享，把它当作"删除旧 + 创建新"，而不是无害的重命名。
- 如果必须删除，备份所有者必须先移除旧共享的备份保护，然后通过获批路径移除锁，重跑一次，并把备份重新应用到最终共享。
- 如果不需要删除，改 IaC 让它避免对受保护共享的破坏性替换。

## 升级规则
- 如果一轮内无法证明锁来源，带证据升级，而不是假定归属。
- 如果阻塞锁位于 RG 或订阅范围，改动前验证爆炸半径。
- 如果同一团队反复命中同一锁模式，开改进项，让所有者和解锁路径显式化。

## 踩坑 / 教训
- 真正阻塞的锁被解决之前，重跑没有帮助。
- 继承的锁会让资源看起来本地已解锁，而真正的阻塞在更高层。
- `ReadOnly` 破坏的操作往往比请求者预期的更多。
- 许多请求者角色缺少权限是正常的；通过受治理的归属解决，而不是宽泛的 RBAC 授权。
- 备份保护锁通常表明一个保管库备份关系，所以干净的修复是备份序列处理，不只是手工解锁。
- 对文件共享，Terraform 中的重命名通常是替换，所以旧共享上的备份保护必须先移除，锁才能清除。
