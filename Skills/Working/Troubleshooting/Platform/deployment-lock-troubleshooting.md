# 平台部署锁排障

> 本技能用于"部署因锁被阻塞且请求者无法移除锁"的事件。第一原则：动任何东西之前，先验证锁是否来自你的编排平台的工作流运行。

## 本技能接受的输入类型
- 应用/项目团队的邮件线程
- 带截图/错误粘贴的聊天线程
- 从 IT 请求系统复制过来的工单文本

## 快速分类
- **问题类别：** 部署解除阻塞 / 治理锁
- **典型错误形态：** `ScopeLocked`、`The scope is locked`、`cannot delete lock`，或重跑老是失败
- **目标资源：** 常在 Test 和 Prod 范围内的 Storage / RG

## 证据优先工作流

### 1. 从邮件/线程规范化请求
触碰资源前先捕获这些字段：
- 环境：Test / Prod
- 订阅、资源组、资源名
- 精确错误文本和时间戳
- 请求者和业务紧急程度
- 请求者是否确认自己没有锁删除权限

### 2. 确认锁存在及其位置
- 检查锁级别：订阅 / RG / 资源
- 捕获锁名、锁类型（`CanNotDelete` / `ReadOnly`）、备注和所有者元数据
- 记录范围路径以便审计追溯

### 3. 判断来源：编排平台还是手工
按这个顺序优先：
1. 检查锁创建时间附近的编排工作流运行历史
2. 把运行操作者/自动化身份与锁元数据对比
3. 在云 Activity Log 中交叉核对锁的 `write` 事件

决策：
- 证据匹配编排运行 → 视为平台治理锁
- 没有平台证据 → 视为非平台/手工锁，做负责人查询

### 4. 路由归属与行动路径
- **平台治理锁：** 与自动化/平台负责人协调一次受批准的解锁/变更
- **非平台锁：** 通过 `team-routing` 路由到所属 Tower，避免绕过归属
- **无权限场景：** 请求者不需要直接删除权；由负责人执行或授予限时访问

### 5. 安全解除阻塞
- 验证业务影响和环境拆分（Test vs Prod）
- 只移除或调整最小必要范围的锁
- 重跑部署并确认成功
- 如果策略要求持久保护，重新应用锁/基线

### 6. 用书面回复收尾
在线程中回复：
- 根因（谁/什么设置了锁）
- 改了什么
- 各环境部署是否成功
- 任何后续治理动作

## 升级规则
- 如果一轮内无法在日志中证明锁来源，带着证据包升级，而不是猜测。
- 如果没有明确的审批路径却请求 Prod 解锁，暂停并升级给平台/首席审批人。
- 如果同一锁模式反复出现，开一条改进任务，避免重复手工解锁。

## 踩坑 / 教训
- 不解决锁来源就重跑部署，只是浪费时间。
- 删除更高级别（RG/订阅）的锁可能意外放开无关资源的保护。
- 许多请求者角色"没有权限"是预期的；通过受治理的归属解决，而不是宽泛的 RBAC 授权。
