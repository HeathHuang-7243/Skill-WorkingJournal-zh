# 平台资源缺失排障

> 本技能用于"部署失败因为工作流本该创建的资源'不存在'"的事件——通常是共享依赖（例如用于 CMK 加密的 Key Vault、Recovery Vault、state 存储）。第一原则：找出**拥有**该资源的工作流，确认它成功了，然后按资源组 + 标签定位资源——不要按更早错误/邮件里的确切名称，因为生成的名称后缀可能每次运行都不同。

## 本技能覆盖的已知模式
- 环境名：`<ENV>-<APP>-<TIER>`（示例）
- 报告缺失的资源：`<资源名>`（来自更早的错误/邮件 —— 只当作提示）
- 所有者工作流：对应编排 WorkflowGroup 中的 **landing-zone 生成器栈**
- 命名模式：`kv-<app>-<env>-<rg>-<随机2字符>-001` —— 2 字符尾部由 `random_string` 产生，每次（重新）应用栈时都会重新生成
- 根因类别：要么原始栈运行从未完成（未创建资源），要么资源以*不同的*随机后缀存在，与更早错误/邮件中捕获的不同

## 本技能接受的输入类型
- 项目/运维团队的邮件线程（例如部署错误粘贴）
- 带截图/错误消息的聊天线程
- 来自 IT 请求系统的工单文本
- 请求者分享的运行截图

## 快速分类
- **问题类别：** 资源缺失 / 配置缺口，不是运行时云故障
- **典型错误形态：** `associated <资源> ... not found`、`resource does not exist`、`404`
- **目标资源：** 由父级配置工作流创建的共享依赖

## 证据优先工作流

### 1. 从邮件/线程规范化请求
触碰任何东西前先捕获这些字段：
- 环境 / 命名空间（例如 `<ENV>-<APP>-<TIER>`）
- 精确错误文本和时间戳
- 错误中所述的资源名（只当作提示 —— 后缀可能已过时）
- 部署者尝试消费的是哪个资源
- 请求者和业务紧急程度

### 2. 识别资源所有者工作流
- 把资源类型映射到创建它的工作流（例如共享保管库 → landing-zone 生成器栈）
- 确认栈的范围：WorkflowGroup、订阅、目标资源组

### 3. 在编排平台上定位 WorkflowGroup
- 从环境命名约定推导
- 打开 WorkflowGroup → 配置栈

### 4. 检查栈的工作流运行
按这个顺序优先：
1. 最新运行状态：**成功 / 失败 / 从未运行**
2. 如果失败：读失败原因（权限、策略、锁、配额、Terraform 错误）
3. 如果成功：确认日志显示资源创建（在日志中搜索资源类型和"Creation complete"）
4. 如果从未运行：确认栈已部署到预期范围并触发初始 apply

### 5. 按资源组 + 标签定位资源，而不是按名称
- **不要**按错误/邮件中的确切名称过滤——随机后缀在各运行之间不同
- 打开所有者工作流目标资源组
- 用匹配的**标签**（应用 ID、环境）和预期的兄弟资源来查找该资源
- 确认消费者的依赖确实接线到了找到的资源（例如在保管库上启用了加密）

### 6. 决定行动路径
| 运行状态 | 可能原因 | 行动 |
|------------|-------------|--------|
| 失败 | 配置被阻塞（锁/权限/策略/配额） | 修复阻塞项，重跑配置栈 |
| 成功且有资源 | 名称后缀不匹配（错误中的名称过时） | 告诉消费者按资源组定位并使用那里找到的资源；后缀是随机的 |
| 成功但资源已消失 | 漂移 / 手工删除 | 通过 Terraform state 恢复或重跑 apply；调查谁删的 |
| 从未运行 | 栈未应用 / 范围错误 | 确认映射，触发初始 apply |

### 7. 用书面回复收尾
在线程中回复：
- 根因（工作流失败/从未运行，或名称后缀不匹配）
- 实际可用的资源（资源组 + 标签 + 全名）
- 指示：消费者应该在资源组下查找，不要依赖旧错误中的名称
- 下游部署现在是否成功

## 升级规则
- 如果配置运行失败是由锁导致的，重跑前先遵循 `deployment-lock-troubleshooting`。
- 如果运行成功但资源消失了，按可能的未授权删除处理；盲目恢复前先经 `team-routing` 路由。
- 如果 WorkflowGroup/栈映射不清楚，不要猜——询问部署目标环境/WorkflowGroup。

## 踩坑 / 教训
- "资源未找到"通常意味着配置工作流从未完成**或者**错误中的名称后缀已过时。
- 生成的名称尾部是 `random_string` 输出——绝不要跨运行硬编码或匹配它们。
- 验证"正确"资源时，用资源组 + 标签 + 兄弟资源的存在性。
- 重跑配置栈会用新的随机后缀重建资源；告诉消费者重新读输出，而不是旧邮件。
- 检查**所有者**工作流（创建资源的那一个）的运行历史，而不是失败的消费者工作流。
- 一次成功的运行显示 `Plan: N to add`（包含该资源、其依赖和相关分配）就是资源已（重新）创建的证明。
