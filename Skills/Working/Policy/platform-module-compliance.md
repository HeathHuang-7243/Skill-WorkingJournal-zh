# 平台模块合规

> 当开发者通过你的**模块仓库 / landing-zone 生成器**部署时，模块自带的是厂商默认值，不总是匹配你的公司策略基线（例如 NIST SP 800-53 Rev. 5 + 内部增补）。这个差距就是不合规。**本技能就是关闭这个差距的循环。**

## 这个循环（记住它——每次项目都遵循）

```
通过模块部署   →   不合规浮现
        ↓
1. 盘点         — 开发者报告他们部署了什么 + 每个模块的不合规状态
2. 分诊         — 按模块分组违规；按 风险 × 量 排序
3. 工作坊       — 把所属团队拉进同一个房间；一次一个模块
4. ADR          — 记录决策（强制执行 / 豁免 / 修改模块）
5. 修复         — 平台团队更新模块；开发者重跑；追踪器关闭
```

## 模块清单（示例 —— 与你的策略评审追踪器保持同步）

| # | 模块 | 默认关注点 |
|---|--------|-----------------|
| 1 | Windows VM | NIST SP 800-53 控制 |
| 2 | Linux VM | NIST SP 800-53 控制 |
| 3 | Function App | NIST 控制 + 日志保留 |
| 4 | Cognitive Services | CMK / 网络隔离 |
| 5 | Storage | CMK + 公共网络访问 |
| 6 | Container Registry | 公共网络、CMK |
| 7 | Load Balancer | 日志 / NSG |
| 8 | Key Vault | RBAC 模式、清除保护 |
| 9 | Managed Shared Disk | CMK |
| 10 | Storage Sync | 私有端点 |
| 11 | File Share | CMK、地域冗余 |
| 12 | Application Gateway | WAF / 日志 |

> 新模块进入追踪器时，用一行**默认关注点**加到这里。这张表是工作坊的索引。

## 阶段 1 —— 盘点（开发者的功课）

每个拥有已部署资源的开发者 / 团队回答：
- **模块名**、**资源数量**、**不合规资源数量**
- **失败的策略**（策略计划 + 控制 ID）
- **负责人**（谁能修复）

输出格式（每个周期粘进一张表）：
```
| 模块 | 资源 | 不合规 | 失败的策略 | 负责人 |
```

不要接受"我们没有"——只要模块部署了，几乎总是至少有 1 条不合规（默认值 ≠ 公司基线，这是定义使然）。

## 阶段 2 —— 分诊（两步 —— 垂直 + 水平）

**步骤 2a —— 垂直（按模块排序）。** 按 **风险 × 量** 给模块排序——为下一次工作坊挑前 4–8 个模块。不要试图在一个会议上覆盖所有模块。

**步骤 2b —— 水平（共享控制族）。** 在安排工作坊之前，扫一遍清单并把每条不合规对着下面的共享控制族打标签。如果 ≥3 个模块命中同一族（日志、CMK、网络隔离……），这个族就成为**它自己的修复流**——不要把它当成 N 个独立的按模块 ADR。一次共享修复关闭全部 N 个。

> **经验法则：** 如果一条发现是"这个模块没把日志送到 SIEM"，并且 3+ 个模块上形态相同，就**不要**开 3 个按模块 ADR。开一个族级 ADR，从每个模块页面上链接过去。

## 阶段 3 —— 工作坊

### 节奏
- 双周一次（积压清空后可改月度）；60 分钟；每场最多 4 个模块
- 常驻出席：**托管/运维**（运行时决策）、**平台/基础设施**（模块所有者）、**安全**
- 只有目标模块排上议程时才拉入模块专属负责人

### 每模块时段（15 分钟）
1. 负责人报告当前不合规数量 + 失败的策略（2 分钟）
2. **默认值 vs 公司** —— 展示模块默认值、展示策略要求、点出差距（3 分钟）
3. **编写 ADR** —— 实时填写 ADR 模板（3 分钟）
4. 行动负责人承诺一个日期（2 分钟）
5. 如需更多讨论则记录"下一步"（5 分钟）

### 两个必须有席位的团队
- **托管/运维团队** —— 拥有运行时/安全决策（网络、身份、补丁）。
- **平台/基础设施团队** —— 拥有模块代码；把 ADR 变成模块变更。

如果工作坊没有这两个团队，改期。没有 Infra 的决策无法实现；没有 Hosting 的决策无法执行。

## 阶段 4 —— ADR（架构决策记录）

每个决策一个 ADR。格式：

| 字段 | 值 |
|-------|-------|
| **ID** | `ADR-NN` |
| **模块** | 哪个模块 |
| **描述** | 一句话决策（例如"Managed Shared Disk 上应启用 CMK"） |
| **状态** | 已提议 / 已接受 / 已拒绝 / 已被取代 |
| **负责方** | 哪个团队负责跟进（安全 / 基础设施 / 托管） |
| **关联模块评审** | 指向追踪器页面的指针 |

在本技能（或链接文档）里维护一个 **ADR 注册表**作为唯一权威来源——ADR 达成当天就追加。别让 ADR 只活在会议纪要里。

## 共享控制族（水平视角 —— 并行推进）

跨多个模块反复出现的发现是**共享平台控制**，不是资源特定异常。只管理一次，并把修复链接回每个触发它的模块页面。

一条在多页反复出现的发现，通常意味着三件事之一：
- **缺失的 landing-zone 基线** —— 没人定义过这个控制的公司值。
- **不一致的模块实现** —— 不同模块带了不同的默认值。
- **尚未跨团队标准化的共享治理要求**。

无论哪种，修复都一样：**抽出一个共享控制族，拥有一次，修复多个。**

### 示例族（从你的跨策略分析中刷新）

| # | 族 | 频率 | 典型修复通道 | 主要所有者 |
|---|--------|-----------|--------------------------|-----------------|
| 1 | **日志与诊断设置基线** | 最高（跨 8+ 模块） | 策略分配 + 可复用模块默认值 + 集中日志模式 | 平台工程、安全 |
| 2 | **带 CMK 的加密** | 高（VM、磁盘、存储、服务） | 标准密钥保管库模式 + 共享加密设计 + 服务特定标准 | 平台工程、安全架构 |
| 3 | **治理计划（NIST SP 800-53 Rev. 5 + ISO 27001:2013）** | 很高 | 一次修复同时关闭两个计划；把每条发现链接到具体策略定义 | 安全、运维、云 |
| 4 | **密钥生命周期与密钥保管库治理** | 中 | 密钥管理标准 + 运营归属模型 + 例外流程 | 安全治理、密钥保管库所有者 |
| 5 | **私有访问 / 网络隔离** | 中 | 参考架构 + 子网与 DNS 模式 + 策略执行 | 网络平台团队、服务所有者 |
| 6 | **计算安全基线** | 中 | 黄金模块标准 + 镜像与扩展治理 + VM 基线策略集 | 计算平台团队 |

> **为什么与模块清单分开？** 模块清单是**垂直的**（每模块一行，每个决策一个 ADR）。族清单是**水平的**（每个反复出现的主题一行，一次修复惠及多个模块）。它们回答不同的问题——不要互相表达。

### 族如何与按模块循环交互

```
按模块工作坊            族级修复
        ↓                               ↓
ADR（按模块）   ←——链接到——→   族流（跨模块）
        ↓                               ↓
  模块变更 /             日志基线（一次）
  豁免 /                 CMK 基线（一次）
  Runbook 变更           网络隔离（一次）
                                       ↓
                              多个模块页面同时关闭
```

**规则：** 如果按模块 ADR 的根本原因是"这个族还没定义"，在开按模块 ADR 之前**先把它提升为族级 ADR**。同一条发现开两个 ADR = 漂移。

### 维护这一节
- **刷新节奏：** 每次工作坊后，把本周新增 ADR 重新对着族清单打标签。只有当 ≥3 个模块命中一个尚未覆盖的主题时，才新增族。
- **不要重复追踪。** 族级修复在途时，**挂起会重复它的按模块 ADR**。只有当族级修复确实不能关闭按模块发现时才重新打开。

## 阶段 5 —— 修复

每个 ADR 路由到恰好三条通道之一：

| 通道 | 发生什么 | 何时完成 |
|------|--------------|-----------|
| **模块变更**（平台/基础设施） | 通过 `devops-userstory-creation` 开用户故事；更新模块代码；开发者重跑 | 模块版本已提升；新部署合规 |
| **策略豁免**（安全） | 带过期时间和负责人的策略豁免；记录在合规注册表 | 豁免已记录；季度评审 |
| **Runbook 变更**（托管/运维） | 更新运维流程（例如日志转发配置） | Runbook 已发布；资源已重配置 |

> **别让 ADR 躺着。** 如果一个"已接受"的决策在表格里没有负责人，工作坊就失败了。离开房间前强制指定负责人。

## 任务（合规就绪清单）

**垂直（按模块）**
- [ ] 追踪器页存在并列出当前范围内的每个模块
- [ ] 追踪器中的每个模块都已指定所属团队
- [ ] 按模块的不合规数量在最近 30 天内刷新过
- [ ] 按节奏召开工作坊 —— 已记录纪要
- [ ] ADR 注册表最新 —— 每个已接受的 ADR 都有负责人 + 关联模块评审
- [ ] 每个 ADR 路由到：模块变更 / 策略豁免 / Runbook 变更之一
- [ ] 已为模块变更开修复工单 / 用户故事（在 ADR 中链接）
- [ ] 季度评审豁免 —— 续期、退役或转为策略

**水平（共享控制族）**
- [ ] 每条不合规已对着族桶打标签
- [ ] 任一被 ≥3 个模块命中的族都有**族级 ADR** 在途（不只是按模块 ADR）
- [ ] 每次工作坊后刷新族清单
- [ ] 被族级修复取代的按模块 ADR 已显式标注挂起

## 踩坑
- **默认值 ≠ 合规。** 厂商模块默认值是给最广泛的客户设计的，不是给你的基线。首次评审时，预期每个模块至少有一个差距。
- **没有 Hosting 和 Infra 的工作坊是演戏。** 与其收集没人能实现的决策，不如改期。
- **没有负责人的 ADR = 愿望，不是决策。** 离开房间前强制指定负责人（具体的人，不是团队）。
- **模块变更是慢车道。** 用户故事比策略豁免耗时更长——设定预期。
- **豁免会过期。** 每个豁免必须有过期时间和评审负责人，否则它会变成永久漂移。
- **Ops 日志之争会重复。** 当模块默认不把日志送到 Ops 的 SIEM 时，预期在每台计算/存储模块上都要吵。把解决方案一次性烤进模块，而不是按资源处理——**这正是 Logging 族存在的原因。**
- **重复族级 ADR 的按模块 ADR = 漂移。** 如果根本原因是"族 X 还没定义"，先提升为族 ADR。
- **NIST 和 ISO 通常是同一发现的两件衣服。** 两个计划在同一个控制上失败时，一次技术修复同时关闭两者——不要开两条并行的计划级 ADR。
- **从不刷新的族清单会腐烂。** 只有当 ≥3 个模块命中一个新主题时才新增族；否则会稀释真正重要的族。
- **CMK 有个叫密钥治理的兄弟。** CMK 是设计决策（用不用 CMK、密钥放哪里）。密钥治理是运营子集（过期、轮换、RBAC）。同一根源，不同归属。不要合并它们，否则一个团队的瓶颈会阻塞另一个。
