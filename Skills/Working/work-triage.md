# 工作分流（每日分类与路由）

> 这是**判断引擎**：对每个传入请求，一步步走过"它是什么、归谁管、要不要协作、能不能自己决定"。
> 静态的"谁负责什么"查询表在 [`team-routing.md`](./team-routing.md)；本文件是决策流程，不是表。
>
> `maturity: evolving` —— 本节**不应冻结**。分类、范围边界和协作信号会被真实工作不断修正和扩展。见底部[学习日志](#学习日志)。

## ① 如何分类（它是什么）

- 按与你角色相关的**领域知识**分类（例如身份/治理、存储、计算、网络、监控），定位这个问题击中哪个专长领域。
- **知会原则：** 即使某主题明确归你处理，也要**知会**所属团队——这是礼貌，不是转交，也不是邀请共管。
- ⚠️ 这个分类在持续演化：新服务、新团队、新边界都应写回这里。

## ② 谁的范围（归属）

**在你的范围内 —— 两种情况：**
1. 任务**完全由你的团队解决** → 你的范围。
2. 最终**治理/所有者是你的团队** → 你的范围。

**不在你的范围（向外路由）：**
3. 资源是**其他团队的主题**，你只协助**配置/实施** → **不在你的范围**；路由给该团队的负责人（经 [`team-routing.md`](./team-routing.md)）。你是协作方，不是所有者。
4. **无策略 / RBAC 涉及**，纯粹是**部署或排障** → 交给**运维团队**。

> **边界（已被使用证实）：**
> - 情况 3 与情况 4 的分界线 = **是否触及治理（策略 / RBAC / 架构所有权）**。情况 3 即使由你完成配置也不在你的范围；所有者是那个团队。情况 4 是纯运维操作、不涉及策略/RBAC——路由给运维。
> - 情况 4 的运维团队和任何 FinOps 负责人是**两条线**——不要混淆。

## ③ 转交 vs 协作

- 归属遵循 [②](#②-谁的范围归属)；经 [`team-routing.md`](./team-routing.md) 路由给所有者。
- **升级信号：** 当某项出现**来回转交（A → B → A → B 乒乓球）**时，"转交"升级为**"协作"**——停止单向传递；把对方拉进来一起解决，避免空转。

## ④ 自行处理 vs 升级（什么我能决定）

**自己决定：**
- 日常运维工作
- 架构 / 解决方案设计的初稿

**必须走流程 / 升级评审：**
- **代码变更** → 先开 **DevOps 用户故事**；与**自动化负责人**和**平台首席架构师**对齐。
- **部署** → 提交**变更请求**；你自己准备，然后由相应负责人审批。
- 任何**创建/修改策略**或**产生成本**的变更 → 需要评审。

> 一句话边界：**策略创建/变更、成本相关、代码、部署 = 升级；日常运维 + 设计草稿 = 自行决定。**

## 踩坑 / 教训

- 这张决策图是**活的**：任何不贴合现有轴的案例都应写回轴或学习日志，而不是硬塞。
- "知会" ≠ "协作"：知会不代表接手工作，也不代表把对方拉进来。
- 误判范围代价很高（要么越界，要么推责）：纯部署/排障且无策略·RBAC → 运维（情况 4）；其他 Tower 拥有的资源 → 该 Tower 负责人（情况 3）；两者都不是你的范围。不确定时，先问一个问题再推。
